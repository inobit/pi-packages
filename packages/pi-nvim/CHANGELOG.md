# Changelog

## [0.1.1] - 2026-10-17

- fix: diagnostics missed late pushes and reported them as clean
  - root cause (measured): push has no completion signal; the old settle gave up after a 3s minimum + 0.5s quiet, while gopls' `slicescontains` analyzer publishes 5-7s after `:edit` (and 7-20s under load) — those waves were lost and the file came back `clean`
  - per-buffer, two-phase flow: `:edit` all buffers -> startup phase (one batched wait until every buffer has an initialized client; each buffer is then judged on its own) -> diagnostic phase (every buffer's pull request is issued at once, callback-driven, and push publishes are observed in the same wait loop, sharing one `diagnosticMs` budget measured from the diagnostic-phase start `t_diag`) -> per-file assembly -> wipe. Buffers no longer serialize: total latency is the slowest one, not the sum
  - routing is per client: pull-capable -> pull only (a failed pull is never retried through push); no pull -> observed through `publishDiagnostics`; formatter-only clients (e.g. oxfmt) are not diagnostics sources and are skipped entirely
  - push data comes from a publish record (`_publishes[client_id+uri] = {at, hash, name, diags}`, empty publishes included) so it survives the batch wipe and carries its own client attribution (the namespace reverse-lookup is gone). A fresh publish (inside the diagnostic window) settles after the observation floor plus a 1.5s quiet period; an old record whose content hash matches and that has been quiet for at least the floor settles instantly (no floor paid)
  - verdicts for unsettled push clients: unfinished `LspProgress` since the request -> `(client) diagnostics timed out`; observed at least the floor while the server is idle -> weak clean (best-effort note in `details` only); observed less than the floor (budget shorter than the floor) -> timeout failure, never clean
  - `timeouts.pushObserveMs` (default 15000, `0` disables): the observation floor. Push has no completion signal, so a floor shorter than the gap between the early empty wave and the late real wave reports a false clean (measured: with an 8s floor a pure-Go batch missed 2 of 4 runs). Pull never pays it; the real fix is enabling `pullDiagnostics: true` for gopls (v0.17+)
  - `timeouts.startupMs` (default 10000) replaces `attachMs` (default 20000) and `timeouts.diagnosticMs` (default 20000) replaces `diagMs`; old keys are still accepted as aliases. The settle knobs (`PI_NVIM_MIN_SETTLE_MS` etc.) are gone with the settle code
  - `nvim_format` pulls post-write diagnostics through the same async path (no push wait: `:w` already gives a definite result for the write itself); the write path is unchanged
  - existence is checked before `:edit` (a missing path used to become an empty buffer that LSPs happily diagnosed)

- fix: diagnostics output could be misread, and daemon-level failures were mixed with file-level ones
  - per-file envelope `{file, status: success|failed|skipped, message?, diags[], ms}`: success never carries a message; failures carry one line (semicolon-joined across clients) and keep whatever partial diagnostics arrived; skipped covers whitelist misses and zero-client files. The pi tool result has no status field (`AgentToolResult` only has content/details), so the state lives in our payload
  - rendering: `clean` / diagnostic lines / `[failed] (client) reason` / `skipped (reason)`; the per-file count lines are gone (the header already totals); lines always use full paths; the header only counts (errors/warnings/hints/failed/skipped) and writes `clean` only when everything is zero
  - LSP failures put the client in a slot (`[failed] (tsc) diagnostics timed out`); bridge-level failures (edit failure, lost buffer, Lua error) have no client slot and fall back to `unknown error` rather than an empty tail. Daemon-level failures (spawn, startup, request timeout) stay batch-level on the tool error channel — no per-file names
  - multi-line diagnostic messages (e.g. oxlint's message plus `help:`) are folded onto one line so a diagnostic is always exactly one line

- feat: per-call timeouts (`nvim_lsp`: `startupMs`/`diagnosticMs`; `nvim_format`: `startupMs`)
  - optional tool parameters; omitted = the user's configured defaults, so existing behaviour is unchanged. Timeout failures name the knob and a suggested value (e.g. `retry with diagnosticMs=40000`), so the model can simply retry with the larger value instead of editing config
  - `timeouts.maxRequestMs` (default 300000) is new: `requestMs` becomes the default window while a call may grow the daemon request window up to `clamp(startup + diagnostic + 5s, requestMs, maxRequestMs)`. Per-phase caps are 120s each, so the largest pair (120+120+5) still fits the 300s ceiling
  - joint clamp invariant `startup + diagnostic + reserve <= window <= maxRequestMs`: over-large asks are scaled down (diagnostic first, down to 1s, then startup) instead of being accepted and then killed by the request window; when values are clamped the content starts with a `note:` line and `details` carries `effective`/`clamped_from`
  - suggested retry values are `max(effective * 2, floor, 2s)` capped by the hard limits, with the diagnostic floor at `pushObserveMs + 5s` and the startup floor at 20s, so one retry is normally enough
  - the bridge re-clamps both fields (120s each) as a defence against malformed requests; `nvim_format` only takes `startupMs` (the write itself has a definite `:w` result)

- docs/prompts: tool descriptions stay basic (what the tool does, read-only vs writes-disk) while every parameter spec — required `files` array, `minimum`/`maximum` for the timeouts, semantics — lives in the tool JSON schema; a new `promptSnippet` finally puts both tools in the system prompt's tool list (custom tools without one are omitted); guidelines stay behaviour-only; every model-visible string (tool errors included) is English; config examples updated in both READMEs

## [0.1.0] - 2026-10-13

- fix: scope abort state per request to close a cross-request leak (reviewer P2-4)
  - retire the global `PiNvim._aborted` / `PiNvim._current` pair in favour of a per-request `_reqs[id].aborted` flag, read everywhere through `aborted(id)`; `wait_attach` / `wait_diag_settled` now take `req_id` from their callers
  - the old hazard: TS throws as soon as the signal fires and can start req-2 while Lua is still finishing req-1 (`vim.wait` pumps the event loop and `remote-send` is reentrant), so req-2's abort set the global flag, the orphaned req-1 left `wait_diag_settled` early, and its `abort_cleanup` deleted the buffer req-2 was still using (req-1 had not wiped it, same handle), failing req-2's `collect_diags` as a `bridge error`. `_reqs[id].aborted` was write-only before, i.e. dead state
  - note: registering before `wait_attach` stays necessary on its own — an abort arriving before registration is still dropped, there is just no global flag left to wipe it
  - regression guard: a source assertion fails if `PiNvim._aborted` / `PiNvim._current` reappear, and requires the wait helpers to accept `req_id` and read `aborted(req_id)`

- fix: stop leaking one sockdir per session (found by real smoke runs) and drop the changed-line count from format
  - **delete `daemon.log` on exit**: `cleanup_sock_dir` used to remove only `nvim.sock` / `ready` / `daemon.pid`, but the log is the daemon's own stderr redirect, so leaving it behind kept the directory non-empty and `rmdir` always failed. Measured: one leaked `$XDG_RUNTIME_DIR/pi-nvim-<session>-<pid>/` per pi session (three smoke runs, three leftovers). Because sibling GC only scans the same session and every session carries a fresh uuidv7, cross-session leftovers were never reclaimed and kept accumulating. The log path now arrives via a new `PI_NVIM_LOG` env instead of a hardcoded cross-language constant
  - **`killStuck` deliberately leaves the log and the directory alone**: a request timeout is exactly when the log is needed to diagnose (the daemon may have been healthy and misjudged), and since the sockdir is keyed by (session,pid) the next spawn reuses the same directory and truncates the log with `"w"`, so keeping it does not accumulate
  - normalize env reads: `vim.fn.getenv` returns `vim.NIL` when unset, which `or fallback` does not catch, so concatenation could fail with "attempt to concatenate a userdata value"; `SOCK_DIR`, the timeouts and `PI_NVIM_LOG` now go through `env_str` / `env_num`
  - add a Lua load check (`nvim --headless -u NONE -c 'luafile bridge.lua' -c 'qa!'`, with and without env, skipped when nvim is absent): Lua syntax and load-time errors are invisible to vitest and surface only as a 30s "daemon start timeout" that the degraded path tolerates without telling the model — breaking `bridge.lua` here (an orphaned `end` left behind by the `count_changed` replacement) was found only through a single `E5112` line in daemon.log
  - **remove `changed_lines`**: format reports success or failure only. `count_changed` / `countChangedLines` compared lines positionally, so an early insertion counted every following line as changed (one inserted line reported three; one inserted at the top reported the whole file) — a number that means nothing to the model. Replaced by a boolean `content_changed`; the field is gone from the Lua results, `FormatFileResult` and details, and the render collapsed from `a.ts: formatted (12 lines)` to `a.ts: formatted`. The dead TS mirror `countChangedLines` is deleted and `deriveFormatState` is kept as contract documentation (the real derivation lives in Lua)

- fix: move format's request registration ahead of the attach wait (release blocker, reviewer follow-up) and close the timeout-hierarchy clamp
  - `PiNvim.format`'s `reg_request` / `reg_bufs` moved from after `wait_attach` to before it, matching `diagnose`: with late registration an abort arriving during the attach window (default `attachMs=20s`, i.e. cold start, exactly when a user is most likely to press esc) was dropped because `_reqs[id]` was not registered yet, and `reg_request`'s `_aborted=false` then wiped the already-delivered abort, so format still ran `:w` and wrote to disk after the user had interrupted — while TS had already returned partial and rendered `aborted before processing`, leaving disk and the model's view of the world in conflict
  - regression guard: a source-order assertion in `test/daemon.test.ts` (`reg_request` before `wait_attach` in both `diagnose` and `format`). The ordering bug cannot be reproduced reliably by smoke (it needs an esc inside a 20s attach window), so the check reads source only and never runs nvim, which keeps the "real daemon behaviour stays out of unit tests" rule; verified to FAIL against the old ordering
  - the timeout clamp is now a shared pure function `clampTimeoutHierarchy`: **clamp `attachMs` before `diagMs`**. The old code only clamped `diagMs` and never touched `attachMs`, so with `requestMs=5000` and the default `attachMs=20000` the expression `Math.max(1000, 5000-20000)` fell back to 1000 and the sum stayed 21000 > 5000 — the invariant was false and a healthy daemon was misjudged as stuck and killed, losing its warmth (reproduced). `diagMs` is now always floored at 1000ms, including when a user sets it lower, so the settle wait cannot be squeezed to near zero and silently miss a cold server's first diagnostics

- fix: request-scoped abort (id-checked delivery), signal listener and uuid resource binding
  - `PiNvim.abort('<req-id>')` arrives with proof: it only raises the flag when the id matches the in-flight request, so a stale abort is dropped and cannot kill a newer request; on the TS side the signal triggers a fire-and-forget send that does not wait for acknowledgement
  - `reg_request` / `reg_bufs` / `abort_cleanup` / `unreg_request`: a per-request id and buffer registry so abort cleanup wipes only this request's resources and never writes res (TS has already returned partial, so a res would be an orphan); three nil-id guards
  - the signal is now observed instead of polled: `listenAbort` (`{once:true}` plus removal in `finally`, preventing cross-call leaks) sends `abort(id)` the moment it fires
  - timeout hierarchy: `attachMs+diagMs<=requestMs`, clamped in both `normalize` and `applyOverlay` with `diagMs` floored at 1000ms, so a healthy daemon is not misjudged as stuck and does not lose its warmth (this clamp had a hole, closed by `clampTimeoutHierarchy` above)

- fix: configurable error-text cap (`errorCap`, default 2000, user-tunable; diagnostics still in full) plus raw passthrough for unrecognised output (`raw` + `note`, never recorded as clean)

- fix: reviewer P2 follow-ups on settle (same batch as the P0): early return on an empty settle list (all edits failed, no need to wait 3s); `PI_NVIM_MIN_SETTLE_MS` env knob (default 3000); clamp `diagMs<=requestMs` so a healthy daemon is not misjudged as stuck; format's per-file `ms` now covers only the write gating, with the settle wait folded into `total_ms`

- feat: first usable release (Phase 1) — dual tools over a per-session headless nvim daemon
  - `nvim_lsp` (read-only diagnostics): single batched daemon round-trip, never writes to disk; files with no client report `diags:[]` + `no_client:true`
  - `nvim_format` (write-back formatting): per-file `withFileMutationQueue` + one daemon round-trip per file; per-file five-state `{formatted, reason(ok/unchanged/no-formatter/format-error/write-error)}` where `formatted` is derived from a before/after content comparison (boolean only, no changed-line count); `:w` failures keep the buffer (no wipe)
  - format simulates the user pressing `:w` (plain `:w` with user autocmds as the formatter pipeline; the bridge never calls `buf.format` explicitly, never uses `noautocmd`, never picks sides)
  - transport: per-(session,pid) socket (`XDG_RUNTIME_DIR` falling back to `os.tmpdir()`, mode 0700), connect probing, `ready`+connect dual ready gate, req/res JSON files with 50ms polling, stale-socket unlink + respawn, same-session sibling GC
  - lifecycle: lazy start (`session_start` prepares paths only), `agent_settled` is a no-op, `session_shutdown` skips `reload` and otherwise fire-and-forget `:lua PiNvim.begin_shutdown()`; daemon-side 5min idle TTL (stops clients + wipes buffers only when idle) and 15s parent-death probe
  - truncation: diagnostics returned in full (structured and reproducible), never truncated; the only cap is 2000 characters of error text (same cap in content and details); the full per-file JSON goes into tool `details`

- fix: wrap up error semantics (diagnostics in full, error text the only thing capped at 2000 chars; the fifth `unchanged` state; severity reading order; three-tier startup health: degraded / surface / force fresh)

- fix: call guard at the `execute` entry (whitelist + pre-check) and neutralised guidelines
  - `whitelist: {enabled, diagnostics:{extensions,filenames}, format:{...}}` (md enters the diagnostics table only, plus the `Dockerfile` filename; `enabled:false` is the full escape hatch), loaded and validated from `config/default.json` and `src/config.ts`
  - TS-side pre-check at the `execute` entry (exists → is a file → readable text → matches this tool's whitelist, in that priority order): missing / directory / unreadable / binary become a per-file `error`, whitelist misses (including unknown extensions and filenames, always fail-closed) become a per-file `skipped` note; mixed batches are split per file and merged back in the original order in a single reply, and a fully blocked batch never calls `ensure()` (the daemon is left undisturbed); only infra failures throw
  - `src/scope.ts` holds the pre-check and whitelist matching (pure functions apart from `probeFileSync`); `result.ts` gains `skipped` row rendering
  - guidelines neutralised to four lines (read-only diagnostics suit verification / format writes to disk, call as needed / pass multiple files in one call + a scope line); the description is unchanged; there is no auto-trigger code

- fix: cold-server diagnostic miss P0 (`wait_diag_settled` becomes batch-level settle)
  - once every client has attached, the whole batch of buffers waits for settle exactly once (continues while new diagnostics arrive; collects after no new diagnostics for 500ms and past a 3s minimum timeline), then each file is collected directly; diagnose and format share this path (per-file settle waits removed, the 10s clamp removed, the budget is always the upper bound)
  - the old logic ("two consecutive unchanged samples mean done") treated "not started yet (temporarily 0)" as "genuinely clean", and since ts only emits its first diagnostics ~2s after attaching during cold start, the first call always missed
  - calibration (local headless measurement of cold-start edit → first diagnostic): ts ~2.5s (three runs: 2475/2477/2505ms), go ~0.6s, py ~0.3s; the `diagMs` default stays at 10000 (measured at roughly 4x headroom, and `config/default.json` and `src/config.ts` were already in sync at 10000), with the per-request override kept
